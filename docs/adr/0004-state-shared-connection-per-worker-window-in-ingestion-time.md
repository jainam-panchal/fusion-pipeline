# State is shared through a per-worker connection, scoped by a handle, with windows measured in ingestion time

The first stateful stage (`dedupe`, issue #6) fixed three things every later stateful stage inherits: how a stage reaches the store, what a key is, and what "within a window" means under redelivery.

**How a stage reaches the store.** The store is one Dragonfly keyspace shared by every worker and every replica of a pipeline, so no sticky routing is needed: two workers racing on the same content both `SET NX` the same key and the server lets one win. What is per worker is the TCP connection, because stages are synchronous and one connection behind a mutex would serialise every worker on each round trip. The engine opens the connections at start, only when some node declares `uses_state`, so a config without state runs without a store and one with state fails fast. Stages never see the connection: the context carries an owned `State` handle (an `Arc` on the worker's connection, so a Lua VM can keep it as `'static` userdata) that prefixes every key with `{pipeline}:{tenant}:{node}:` and counts every operation on the `state_*` metrics. Isolation between tenants and pipelines is therefore structural, not a convention a stage author or an operator can forget. The pipeline name comes from the config (`name:`), since it is data like the nodes; replicas of one pipeline share state, different pipelines on one store must be named apart. A stage that cannot reach the store returns `StateError { record, error }` and the engine applies the node's `on_state_error`; the stage only reports.

**What a key is.** One string key per distinct content, `SET key value NX PX window GET`, the value being the record id and its ingestion time. Considered and rejected: a Bloom filter (a false positive drops a real record, and it cannot hold the id, so a redelivered record would be dropped, exactly on the chaos test); a Bloom in front of the exact check (every first sighting is a write anyway, so it adds a round trip and saves nothing); a hash per node (fields have no TTL on this server without a script); a set per bucket (no id, and the bucket seam below); a sorted set (a script for atomicity and two structures to hold the id). Exact dedupe must remember every content in the window, so memory is O(unique contents) whatever the structure; the content is hashed (FNV-1a 64, about 200 ns against a 50–300 µs round trip; 3% chance of one collision at a billion live keys per scope, the point to move to 128 bits) so a key is about 200 bytes whatever the body size.

**What a window means.** The window is the key's TTL, measured in ingestion time (`observed_time_unix_nano`, filled from the JetStream publish time when the producer set nothing), not on arrival at the stage. The arrival-time reading, and the spec's original "value is the record id" rule, had a hole the review found: a record passes, the process dies before the ack, the key expires, a newer duplicate claims it, and the redelivery, arriving after `ack_wait`, reads a foreign id and drops. A real record lost. Closing it by rule (`window` longer than every possible redelivery) ties the window's meaning to the consumer's settings; closing it with a per-record memo costs a second round trip per record. Reading the stored ingestion time closes it for free: the redelivered record is older than the holder, so it cannot be the holder's repeat, and it passes. Time buckets in the key name were rejected because two records 20 ms apart across a boundary both pass, and a sliding window (refresh on every repeat) because it changes the spec's "after the window a repeat passes again".

## Consequences

- `Context` is `Clone`, not `Copy`; the `Stage` trait gains `uses_state` and `on_state_error`, both with defaults, and `StageOutput` a sixth variant. CLAUDE.md's stage invariant lists it.
- Three imperfections, all an extra copy and never a loss: an older record arriving after a newer one with the same content passes, a duplicate delayed longer than the window passes, and two records past the window arriving on two workers at once both pass. At-least-once prefers the copy.
- Producer clocks decide windows. A producer with a skewed clock affects dedupe only within its own tenant and only by its skew.
- Values the engine's own stages write are one line, space-separated, with the record id as the first token (`dedupe` writes `"{id} {ingestion time}"`). Lua values (#8) are the script's bytes and follow no rule. A shared value type waits until a second engine-written format exists.
- Five operations: the spec's four plus `set`, the unconditional write. A record past the holder's window must take the key over, or the holder's key lives on until its server-side TTL and every record of a replayed burst passes; `set_nx` cannot do that and `del` then `set_nx` races (a second worker's `del` would erase the first's fresh claim). `incr` sets the ttl on every call.
- A paused store (the chaos test) becomes a `StateError` within the 2 s operation timeout and the connection is reopened on the next call, because a reply that arrives after a timeout would otherwise answer the next command. The compose pipeline sets `on_state_error: nak` so the pause holds records back instead of forwarding duplicates.
- Later modes (sliding, fixed buckets, count instead of drop) and a scope override are new fields with today's behaviour as the default; none changes the keys written now.
